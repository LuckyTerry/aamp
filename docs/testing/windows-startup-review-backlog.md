## WIN-STOP-001：旧后台未及时退出时，stop 长时间无反馈

- 记录日期：2026-09-28。
- 状态：待统一 review，暂不修改实现。
- 验收代码：`fix/feishu-auth-scope-negotiation`，`fa78f51`。
- 场景：使用本地修复版在管理员 PowerShell 执行 `stop`，停止此前由全局旧版启动、已持续运行的后台。
- 现象：终端长时间没有细节输出，看起来卡住；停止请求已写入，但旧 Worker 和 Controller 在检查时仍然存活。后续确认本次前台及旧后台均已退出。最终计划任务已不存在，不能据此认定是 `stop` 删除了任务（正常 stop 仅禁用任务）。排查期间未人工终止进程或删除任务。

### 已确认的实现问题

`packages/aamp-feishu-task-agent/bin/windows-service.mjs` 的 `stopUnlocked()` 使用次数控制多个等待循环，默认 `stopAttempts = 100`。等待 Controller 退出的循环每次都会执行完整 `readIdentity()`，再等待 100 毫秒。

身份查询需要启动 PowerShell 并执行 CIM 查询，其耗时也计入实际等待。因此总耗时并非 100 × 100 毫秒，可能达到分钟级；其他阶段还包含额外查询。当前没有停止阶段和累计等待时间提示。

旧 Controller 为什么未及时退出仍需进一步定位，不能仅根据循环耗时认定其内部阻塞原因。

### 测试覆盖缺口

此前隔离权限矩阵使用能及时响应停止请求的合成 Controller，验证了跨权限启停，但没有覆盖旧后台不响应或迟迟不退出、身份查询较慢时的完整等待路径。此前测试通过不代表该场景已通过。

### 待 review 的方向（未批准实施）

1. 根据实际耗时设置停止阶段预算，而不是仅限制轮询次数；将查询本身的耗时和超时纳入预算。
2. 到达温和停止等待期限后，核验身份并进入现有强制停止流程；保留 PID 复用、所属用户和启动代次校验。
3. 输出停止阶段、等待耗时和转入强制停止的原因；成功、失败、取消均清理提示定时器，避免持续写日志。
4. 分开报告“已发停止请求”“确认进程退出”“计划任务状态”，不得在后台仍存活时报告停止成功。

### 后续验证要求

- 先复现：合成后台忽略停止请求，并模拟或实测慢身份查询，观察现有等待上限被查询耗时放大。
- 修复后验证：停止耗时受明确预算约束（包含查询超时）；超时后只结束身份匹配的所属进程。
- 覆盖 PID 复用、查询拒绝、代次变化、已有后台及时退出和强制停止失败。
- 在真实旧版后台上复验，并确认终端返回、停止状态准确、无残留提示定时器。
