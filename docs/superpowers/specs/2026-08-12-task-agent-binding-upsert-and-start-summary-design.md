# Task Agent 绑定增量保存与启动摘要设计

状态：已于 2026-08-12 完成方案确认，尚未开始实现。

## 背景

`feishu-task-agent install` 当前在成功绑定后会用本次结果整体覆盖
`~/.aamp/feishu-task-agent/bindings-v1.json`，导致此前保存的其他绑定消失。
`add` 虽然采用追加写入，但遇到相同 `app_id` 时只会报错，无法让用户主动更新
Bot 与本地智能体之间的绑定关系。

此外，`install` 和 `start` 的结束摘要目前只显示成功数量。用户一次启动多个配置时，
无法从摘要直接确认哪些配置成功、哪些配置失败。

## 目标

1. `install` 改为保留已有绑定并增量保存本次选择。
2. `install` 和 `add` 遇到相同 `app_id` 时，经过用户明确确认后原子替换旧绑定。
3. 新配置先以 `pending` 状态原子写入，再进行配对和启动；启动失败不撤销绑定。
4. 启动摘要保持原有“成功数/计划启动数”统计口径，并列出成功和失败的具体绑定。
5. 不热切换正在运行的 Bridge；配置变更统一在下一次 `start` 时完整生效。

## 非目标

- 不允许同一 `app_id` 同时存在多条绑定。
- 不复用旧绑定的 `binding_id`、runtime 目录或 Agent mailbox。
- 不因 `add` 或重复绑定替换而停止当前正在运行的 Bridge。
- 不改变当前“至少一个配置成功即可保持整体运行；全部失败才退出”的启动策略。
- 不改变全局 runtime-session lease、配置路径或配置 schema 版本。

## 方案选择

采用按 `app_id` 执行“确认式 upsert”的方案：

- 新 `app_id` 追加到列表末尾。
- 已有 `app_id` 先展示旧绑定和拟替换的新绑定，并请求用户确认。
- 用户确认后，在旧绑定原有位置写入一条全新的 `pending` 绑定。
- 用户拒绝后保留旧绑定，本次选择记为取消，不记为系统失败。

没有采用以下方案：

- 先删后加：新记录写入失败时会丢失旧绑定。
- 原地复用旧 `binding_id`：容易错误继承旧 runtime 路径、mailbox 和 ready 状态。
- 同一 `app_id` 保存多条绑定：会让 Bot 事件归属和启动选择变得不确定。

## 数据与原子性

### 绑定身份

Bot 的唯一键继续使用 `bot.app_id`。替换后的记录使用：

- 新生成的 `binding_id`；
- 与新 `binding_id` 对应的新 runtime 路径；
- 新选择的 `agent_type`、Bot 授权信息和 lark-cli profile；
- `state: pending`；
- 新的 `created_at` 与 `updated_at`；
- 不包含旧记录的 `agent_target_email` 和 `runtime` 字段。

### 原子写入

新增一个批量 upsert 持久化入口，在现有配置文件锁内完成一次读、校验、合并和
原子 rename 写入：

1. 重新读取最新 store，避免交互期间配置已被其他命令修改。
2. 再次检查 `app_id` 冲突及用户已经确认的替换集合。
3. 将替换项写到旧项原位置，将新增项追加到列表末尾。
4. 校验合并后的 store 不含重复 `binding_id` 或 `app_id`。
5. 通过现有 `writeJsonAtomic` 一次性提交完整配置。

`install`、`add` 和 `remove` 继续由 mutation lock 串行化。若确认以后、真正写入以前，
同一 `app_id` 被另一进程新增或改变，本次写入必须中止并提示用户重新执行，不能静默
覆盖一个未经确认的新状态。

## 交互流程

### 重复绑定确认

选择 Bot 并获得 `app_id` 后，若 store 中已存在该 `app_id`，展示类似内容：

```text
Bot cli_xxx 已存在绑定：codex ↔ Codex Bot (cli_xxx)
拟替换为：traex ↔ Codex Bot (cli_xxx)
是否替换绑定？[y/N]
```

- 选择“否”：保留旧绑定，将该选择加入取消项，允许继续选择其他配置。
- 选择“是”：将该草稿加入待 upsert 集合。
- 同一次交互中已经选择过的 `app_id` 仍禁止再次选择，避免对同一目标产生两份相互
  冲突的替换意图。

如果命令执行期间已有 Bridge 在运行，保存成功后补充提示：配置变更将在下一次
`feishu-task-agent start` 时生效；当前 Bridge 不受影响。

### `add`

`add` 完成所有选择后，批量原子 upsert 为 `pending`，不执行 ACP 配对，也不启动
Bridge。新绑定和替换绑定都在下一次 `start` 中完成首次配对。

### `install`

`install` 的顺序调整为：

1. 完成选择与重复绑定确认。
2. 将所有已确认的新绑定或替换绑定批量原子写为 `pending`。
3. 对本次成功写入的绑定逐项准备 Agent、完成配对并启动 Bridge。
4. 单项启动成功后，将对应记录原子更新为 `ready`。
5. 单项准备、配对或启动失败时，保留其 `pending` 记录，供之后执行 `start` 重试。
6. 本次没有任何成功写入项时，不启动 Bridge，也不改变已有配置。

配置保存成功与 Bridge 启动成功是两个独立结果。错误文案必须区分“绑定未保存”和
“绑定已保存但启动失败”，避免用户重复创建 Bot。

## 启动结果摘要

`start` 和 `install` 共享统一的结果摘要输出。分母继续表示本次计划启动的配置数，
包括失败或用户在准备阶段取消的配置。例如计划启动 2 个、成功 1 个、失败 1 个：

```text
已成功启动 1/2 个配置。
启动成功：
- codex ↔ Codex Bot (cli_success)

启动失败：
- traex ↔ Trae Bot (cli_failed)
  原因：Trae CLI Next 未登录

🟢 保持终端打开，你可以给 agent 派发飞书任务
```

具体规则：

- 成功清单使用最终实际运行的绑定；Agent 类型发生准备期归一化时展示最终类型。
- 失败清单展示绑定标签和已脱敏的最终失败原因。
- “启动失败：”紧跟成功清单，不在标题前额外输出空行。
- 用户取消项单独列为“已取消”，不混入失败清单。
- 只有存在对应项时才显示成功、失败或取消章节。
- 至少一个 Bridge 成功时继续监督这些进程；全部失败时仍按现有逻辑退出。
- `install` 可继续使用“已成功建立绑定并启动”作为标题，但采用同一套清单和统计规则。

## 并发与运行中变更

- `start` 运行期间执行 `add` 并确认替换，只修改持久化配置，不停止或替换旧 Bridge。
- 已被替换或移除的旧 Bridge 会持续运行到原 `start` 进程退出。
- 下一次 `start` 读取新的配置快照，才会使用新绑定。
- `install` 仍受全局 runtime-session lease 约束，不能与一个正在运行的 `start` 并行
  进入绑定和启动流程。

## 错误处理

- 用户拒绝替换：不是错误，旧配置保持不变。
- 原子 upsert 失败：任何本次选择都不落盘，不进入启动阶段。
- 配置写入成功但启动失败：保留 `pending`，在摘要失败清单中展示原因。
- `ready` 状态更新失败：停止对应本次新启动的 Feishu Bridge，保留可诊断错误，避免
  运行态与持久化状态静默分叉。
- 所有错误输出继续使用现有 secret redaction，不展示 App Secret。

## 测试方案

按 TDD 增加以下回归覆盖：

1. `install` 新增绑定时保留所有旧绑定。
2. `install` 和 `add` 的重复 `app_id`：拒绝时 store 不变，确认时在原位置原子替换。
3. 替换记录使用新 `binding_id`、新路径和 `pending` 状态，且不继承旧 runtime 字段。
4. 同一交互内重复选择同一 `app_id` 会被拒绝。
5. 并发校验发现确认对象已变化时，整批 upsert 失败且配置不产生部分写入。
6. `install` 在启动前已经保存 pending；启动失败后记录仍存在，之后可由 `start` 重试。
7. `add` 替换时不启动 Bridge，并输出下次 `start` 生效提示。
8. 摘要在部分成功时保留 `1/2` 口径，分别列出成功绑定、失败绑定及脱敏原因，并且
   “启动失败：”标题前没有额外空行。
9. 全部成功、全部失败和用户取消场景不输出空章节，并维持现有进程监督语义。
10. 运行 Task Agent 全量测试、Bootstrap `bash -n`、Node 语法检查和 `git diff --check`。
